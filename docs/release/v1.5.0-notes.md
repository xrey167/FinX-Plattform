# Release Notes — v1.5.0

> **Status: pending tag.** Bundles the OpenBB-parity Phase 4 program — 11 waves,
> PRs #419–#428 — merged to `main` after the v1.4.0 tag.

The **OpenBB command-parity release.** v1.5.0 closes the real OpenBB
command-breadth gap. The endpoint catalog grows from **131 routes** (v1.4.0) to
**216 routes / 185 provider candidates** — **169 `Fetch` routes** (up from 84) +
**47 `Compute` routes** — with full parity on the **keyless / free-key**
provider surface. The remaining OpenBB commands require *paid* provider keys or
have no public API; those are documented deferrals (a business decision, not an
engineering gap), enumerated honestly in the gap matrix.

This is a **MINOR** release: all changes are backward-compatible additions.
No protocol, persistence-schema, or operator-contract breaks.

## Why this release exists

Through v1.4.0, the OpenBB-parity phases (P1–P3) had closed a *keyless,
standardizable subset* of OpenBB's ~306-command surface, but provider-fetch
coverage was only ~38% (84 of ~223 provider-backed commands). v1.5.0 (Phase 4)
closes that gap to **~90% of the keyless-achievable surface**, built clean-room
from each vendor's own public API docs — never from OpenBB source.

## Engineering notes

- Every route is clean-room: a `<Provider>Raw` serde struct normalizes to a
  standard `tdw-domain` model (no raw shapes leak past the fetcher) → a catalog
  route with ordered provider candidates → a daemon dispatch binding.
- Every wave was 3-lens adversarially reviewed and folded the automated
  Gemini-code-assist review (HIGH/MEDIUM findings fixed forward), and passed the
  three-artifact drift gate (OpenAPI, Python SDK, Workspace widgets golden) plus
  the clippy pedantic+nursery ratchet at 0.
- A final read-only architect gate assessed the cumulative deliverable: parity
  claim honest, architecture consistent, no fabricated endpoints — verdict
  CLEAR.

## Upgrade notes

- **No breaking changes.** New routes are additive; existing routes and the
  daemon/MCP/REST contracts are unchanged.
- New providers resolve through the existing provider-candidate path; keyed
  providers stay dormant unless their key is configured.
